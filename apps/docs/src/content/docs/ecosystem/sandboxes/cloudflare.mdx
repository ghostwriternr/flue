The Cloudflare sandbox gives a Flue application deployed on Cloudflare a container-backed Linux environment, on [Containers](https://developers.cloudflare.com/containers/). Flue ships `FlueSandbox`, the Durable Object that runs each sandbox's container. The integration is platform-native: it is not an adapter module for a Node-target application, and it needs no extra package.

## Quickstart

Add container-backed Linux sandbox capability to an existing Flue project with the Cloudflare Sandbox blueprint.

<CopyPrompt text="Run `flue add sandbox cloudflare` and follow the blueprint to add a Cloudflare Sandbox to this Flue project." />

Copy this prompt into your coding agent. The blueprint the agent fetches is an implementation guide, not an installer — the agent reads it, then inspects and modifies your project. It may:

- Upgrade `@cloudflare/vite-plugin` and `wrangler`.
- Add the `FlueSandbox` container entry and a new migration entry to `wrangler.jsonc`.
- Create or update the container `Dockerfile`.
- Define the sandbox in `cloudflare.ts` and attach it in your Flue agent with `useSandbox(...)`.
- Inspect the existing project structure and avoid overwriting incompatible setup.

If your project currently targets Node, the blueprint will stop and confirm with you before migrating the whole project to the Cloudflare target — the Cloudflare sandbox only runs inside a Worker.

Before you start, check two prerequisites:

- **Workers Paid plan.** Containers are a Workers Paid feature. See [Containers pricing](https://developers.cloudflare.com/containers/pricing/).
- **Docker for local development.** `vite dev` builds and runs the container image locally, so the Docker daemon must be installed and running. Deployed Workers do not need Docker.

## Overview

A sandbox definition says how a kind of sandbox runs. Export it from `cloudflare.ts`, then use it in agents:

```ts title="src/cloudflare.ts"
import { cloudflareSandbox } from '@flue/runtime/cloudflare';

export const workspace = cloudflareSandbox();
```

```ts title="src/agents/coding-agent.ts"
'use agent';
import { useModel, useSandbox } from '@flue/runtime';
import { workspace } from '../cloudflare.ts';

export function CodingAgent() {
	useModel('anthropic/claude-opus-4-7');
	useSandbox(workspace);
	return 'You have a full Linux sandbox. Use it to complete whatever the user asks.';
}
```

Each sandbox is one container and one workspace, run by one `FlueSandbox` Durable Object, and is identified by its definition's export name and a **sandbox id**. The id defaults to the agent instance id, so each agent instance gets its own sandbox. Agent shell and file operations all run as commands in the container.

Containers have no control plane of their own, so `FlueSandbox` plays that role:

- **Start.** The first call after a stop starts the container, restoring the workspace from its snapshot.
- **Idle stop.** After `idleTimeoutMs` (10 minutes by default) with no call from any attached agent and no running command, Flue snapshots the root filesystem and stops the container. A running command keeps the container alive, even after the agent that started it has gone.
- **Unexpected loss.** When a container stops without Flue stopping it (a crash, running out of memory, eviction), the next call restores the last snapshot, or starts a fresh workspace when there is none. The model is told before its next turn, with an `environment` signal saying the workspace was restored to an earlier time or reset.
- **Cancellation.** Aborting a command kills its whole process group in the container. A `timeoutMs` deadline runs inside the container, so it holds even if a Durable Object restarts.

## Configure

| Requirement                      | Purpose                                                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Cloudflare target                | **Required** — Runs the platform-native sandbox integration.                                                     |
| Workers Paid plan                | **Required** — Containers are a Workers Paid feature.                                                            |
| Docker (local development only)  | **Required for `vite dev`** — Builds and runs the container image locally; not needed for deployed Workers.      |
| `FlueSandbox` container          | **Required** — The `containers` entry and migration in `wrangler.jsonc`.                                         |
| Container image                  | **Recommended** — Defines the Linux filesystem and tools; without one, sandboxes use `cloudflare/debian-trixie`. |
| `@cloudflare/vite-plugin` 1.63+  | **Required** — Supports the `durable_object` scheduling policy. Needs `wrangler` 4.150 or later.                 |
| Environment-variable credentials | **Not required** — Route authenticated APIs through intercepts instead.                                          |

Declare the `FlueSandbox` container entry and append a migration in `wrangler.jsonc`:

```jsonc title="wrangler.jsonc (excerpt)"
{
	"migrations": [
		// ...existing entries, unchanged...
		{ "tag": "flue-sandbox", "new_sqlite_classes": ["FlueSandbox"] },
	],
	"containers": [
		{
			"class_name": "FlueSandbox",
			"name": "my-app-sandbox",
			"scheduling_policy": "durable_object",
			"images": { "default": { "dockerfile": "./Dockerfile" } },
		},
	],
}
```

`flueWorkerConfig()` adds the `FlueSandbox` Durable Object binding and rejects an entry that lacks `"scheduling_policy": "durable_object"` or sets `image`, `instance_type`, or `max_instances` (each definition chooses its instance type). The generated Worker exports `FlueSandbox`.

The image must provide `bash`, coreutils, findutils, util-linux `setsid`, and a long-lived main process. Use `tini` as the entrypoint so killed processes are reaped:

```dockerfile title="Dockerfile"
FROM node:24-trixie-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
      bash ca-certificates git ripgrep tini procps \
    && rm -rf /var/lib/apt/lists/*
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["sleep", "infinity"]
```

Image `ENV` lines do not reach agent commands. Commands start from a fixed baseline (`HOME`, `LANG`, `TERM`, and a Debian `PATH`); pass the rest when [attaching](#attach).

## Settings

```ts title="src/cloudflare.ts"
export const workspace = cloudflareSandbox({
	image: 'default', // key in the container entry's images map
	instance: 'standard-1',
	enableInternet: true,
	persist: true,
	idleTimeoutMs: 10 * 60_000,
});
```

Settings are code: Flue reads them from the definition on every container start, so a deploy that changes them reaches existing sandboxes. New intercepts and the idle timeout apply as soon as the deploy is live, `instance` and `enableInternet` at the next start, `persist` at the next idle stop, and `image` the next time the sandbox boots from its image (see [Persistence](#persistence)). Intercepts cannot be removed from a running container, so removing one takes effect at the next start; call `reset()` to apply it now.

Pass a function to vary settings per sandbox. It receives the sandbox `id`, the Worker `env`, and the Worker's `exports`, and runs on every start:

```ts
export const workspace = cloudflareSandbox(({ id }) => ({
	instance: id.startsWith('build:') ? 'standard-4' : 'standard-1',
}));
```

`instance` defaults to `standard-1`. The platform's smaller `lite` instance has 1/16 of a vCPU and 256 MiB of memory: each command takes most of a second, and installing packages takes minutes. See the [Sandbox API reference](/docs/reference/sandbox-api/#cloudflaresandboxsettings) for every setting.

### Definitions and identity

The export name is part of each sandbox's identity: renaming `workspace` starts new, empty sandboxes. To rename a definition in code, keep exporting it under the old name too (`export { builder as workspace }`). A definition must be exported from `cloudflare.ts` before an agent can use it; define as many as you need, one per kind of sandbox.

## Attach

`useSandbox(workspace)` gives each agent instance its own sandbox. `attach()` sets how one agent attaches:

```ts
useSandbox(
	workspace.attach({ id: 'repo-42', cwd: '/workspace/app', env: { NODE_ENV: 'development' } }),
);
```

- `id` — the sandbox id; default: the agent instance id.
- `cwd` — the working directory, created on every start; default: `/workspace`.
- `env` — environment for this agent's commands, layered over the baseline. Not for secrets: use [intercepts](#secure-egress).

## Persistence

With `persist: true` (the default), the workspace survives idle stops: Flue snapshots the container's root filesystem when it stops it and restores the snapshot at the next start. Installed packages, build caches, and files outside `cwd` all persist.

- A snapshot takes a few seconds and does not pause running commands. Under `vite dev`, snapshots are Docker commits instead: they pause the container while they run, and each one leaves a `workerd-container-snap-*` Docker image behind; remove those with `docker rmi` when you no longer need them.
- A persisted workspace keeps the image its snapshot was taken from: the snapshot includes the whole root filesystem. Redeploying with a new `Dockerfile` or `image` affects new sandboxes, reset sandboxes, and sandboxes with `persist: false`. To move a workspace to a new image, copy the files you need out, `reset()` it, and copy them back.
- Snapshots expire after Cloudflare's retention period. A sandbox whose snapshot has expired starts with a fresh workspace and the model is told it was reset.
- With `persist: false`, each stop discards the workspace, and the next start begins from the image.

Snapshots are not checkpoints of conversation state. Keep knowledge the agent must not lose in [persistent state](/docs/guide/durability/#persisted-state).

## Shared sandboxes

Agents that attach to the same definition with the same `id` share one sandbox: one container, one workspace, and one network identity. Use separate `cwd` values to keep their files apart.

```ts
useSandbox(workspace.attach({ id: `project:${projectId}`, cwd: '/workspace/reviewer' }));
```

## Secure egress

Intercepts route outgoing HTTP and HTTPS requests from the container through your Worker, so credentials never enter the container. Export a `WorkerEntrypoint` from `cloudflare.ts`:

```ts title="src/cloudflare.ts"
import { WorkerEntrypoint } from 'cloudflare:workers';

export class GitHubProxy extends WorkerEntrypoint<Env> {
	async fetch(request: Request) {
		const headers = new Headers(request.headers);
		headers.set('Authorization', `Bearer ${this.env.GITHUB_TOKEN}`);
		return fetch(request, { headers });
	}
}
```

Then route a host to it from a settings function, which receives the Worker's `exports`:

```ts title="src/cloudflare.ts"
export const workspace = cloudflareSandbox(({ id, exports }) => {
	const github = exports.GitHubProxy({ props: { sandboxId: id } });
	return {
		intercepts: [{ host: 'api.github.com', https: true, target: github }],
	};
});
```

An intercept's `target` is any `Fetcher`: an exported entrypoint from `exports`, or a service binding from `env`. Use `{ all: true, target }` to route all outbound HTTP. Read secrets from `env` in the entrypoint, and pass what varies per sandbox, such as its id, as `props` (the entrypoint's `ctx.props`). Flue applies intercepts on every container start, and again when a deploy reloads a sandbox whose container is running.

## Container start hook

For setup that intercepts cannot express, such as a background process that should run whenever the container does, use `onStart`:

```ts title="src/cloudflare.ts"
export const workspace = cloudflareSandbox({
	async onStart(container) {
		const daemon = ['sh', '-c', 'my-daemon >/var/log/my-daemon.log 2>&1 &'];
		await (await container.exec(daemon)).output();
	},
});
```

Flue calls `onStart(container, { id, env, exports })` on every container start, after it prepares the container and applies the intercepts, and before any command runs. Throwing fails the start.

## Manage a sandbox

`getCloudflareSandbox(harness.sandbox)` returns building blocks for the sandbox an agent runs on. Anywhere in the Worker, such as an admin route, look one up by id on its definition:

```ts
import { workspace } from './cloudflare.ts';

const sandbox = workspace.get(env, sandboxId);
const { running, generation } = await sandbox.status();
```

- `status()` — running state, workspace generation, last workspace change, and the snapshot the next start restores from.
- `checkpoint()` — take a snapshot now; the next start restores from it.
- `reset()` — discard the container and its snapshot; the next call starts fresh.
- `fetch(port, request)` — send an HTTP request to a server in the container, for example a preview.

## Upgrading from `@cloudflare/sandbox` 0.x

The 0.x form, `cloudflareSandbox(getSandbox(env.Sandbox, id))`, still works through Flue 2.x with a deprecation warning and is removed in 3.0. To upgrade, run `flue update sandbox cloudflare` and follow the blueprint's version 2 upgrade guide. In short: replace the `Sandbox` binding and container entry with the `FlueSandbox` entry, add one migration that deletes `Sandbox` and adds `FlueSandbox`, give the container a new `name`, switch the Dockerfile off `cloudflare/sandbox`, export a `cloudflareSandbox()` definition from `cloudflare.ts`, and pass it to `useSandbox()`. Direct calls on the 0.x stub move to the [handle](#manage-a-sandbox): `destroy()` becomes `reset()`, and requests to a port in the container go through `fetch(port, request)`. Deploy the migration at 100%, then delete the old container application. Workspaces in 0.x containers do not carry over.

## Choose this integration when

Use the Cloudflare sandbox when an agent on Cloudflare needs git, package installation, native binaries, or other Linux tooling. Prefer [Cloudflare Computer](/docs/ecosystem/sandboxes/cloudflare-computer/) when a durable workspace and shell-expressible work are enough and a Linux toolchain is unnecessary.

Treat network egress, mounted data, credentials, and side effects as application security decisions. See [Sandboxes](/docs/guide/sandboxes/#remote-sandboxes) and [Deploy on Cloudflare](/docs/ecosystem/deploy/cloudflare/).
